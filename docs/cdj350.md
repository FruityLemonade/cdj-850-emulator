# CDJ-350 bring-up

The CDJ-350 runs on the same MAIN board as the CDJ-850, so the `cdj350`
machine is the `cdj850` board with a different panel CPU on the SCIF1 link.
This page records what is known so far. Addresses are in the CDJ-350 v1.14
MAIN image (`C350MAIN.UPD`, unpacked to 0x0C000000). The Ghidra entries are
in `scripts/ghidra/cdj350-annotations.json` (program `c350_main_unpacked.bin`)
and the service manual is digested in `docs/cdj350-service-manual.md`.

## Hardware (CDJ-350 service manual RRV4069; details in `cdj350-service-manual.md`)

| Part | CDJ-850 | CDJ-350 |
|---|---|---|
| MAIN CPU IC103 | R5S72630P200FP (SH7263) | same |
| Audio DSP IC301 | DSPC56371AF180 | same |
| SDRAM IC102 | K4S561632J-UC75, 32 MB | same |
| Servo IC201, driver IC204, DAC IC302, USB switch IC107 | TC94A15FG, BD7956FS, PCM1742KE, TS3USB30RSW | same |
| Flash IC101 | DYW1796 | DYW1792 (ID and sector map unverified; the machine uses the CDJ-850's) |
| Panel CPU | IC1007 PEG799A8 | IC501 M3030RFCPFP (M16C), on PNLB |
| Link nets (CN502) | TSCK, TSO, TSI, PNL_XBUSY, MAIN_XBUSY | TSCK, TSCS, TSO, TSI, PNRDY |
| Display | dot-matrix DATA FL + jog FL | one FL tube (V501), no jog display |

## Firmware container

`C350MAIN.UPD` has the same layout as `C850MAIN.UPD`: a flat big-endian flash
image with the reset vectors at 0 (PC 0x100, SP 0xFFF90000), the label
`CDJ-350 MAIN` + `1.14` at 0x60000, the BE32 packed-MAIN length at 0x60020
(0x190BC5) and the LZSS stream at 0x60024. The bootloader region (0..0x40000)
is its own build. The bootloader decodes MAIN to 0x38FFE0 bytes. The longer
0x3A587D-byte extract also includes bytes decoded past the declared stream.
The DSP56371 program's
first SHI segment is at 0x0C1406B8 (CDJ-850: 0x0C155B28).

`scripts/firmware/prepare_firmware.sh --model cdj350 [--install] C350MAIN.UPD`
builds and checks the images (`c850_raw`, `make_flash_cdj850` and
`c850_unpack` take the CDJ-350 container; the update itself is checked
against `MODEL_UPD_SHA256` first). With `CDJ_MODEL=cdj350` in `cdj.conf`,
`./start.sh` runs the `cdj350` machine in a window with the USB stick.

## Boot

On the `cdj850` board with no changes, the firmware boots through its own
bootloader, uploads and starts the DSP program over SHI, completes panel
transactions from about 0.5 s, and with no media shows `EJECT` and then
`NO DISC`, as the CDJ-850 does.

## Panel link

The driver mirrors the CDJ-850's: SCIF1 at 0xFFFE8800 as a clock-synchronous
slave (`scif1_panel_setup` 0x0C0E5800), IRQ5 (vector 69, PNL_XBUSY) at
0x0C0E594A and TXI1 (vector 199) at 0x0C0E59B2, from the handler table at
0x0C177C84. A transaction is always two 16-byte full-duplex frames.

### Panel to MAIN

| Frame | Checked | Kept |
|---|---|---|
| 1 | 8-bit end-around-carry sum of bytes 0..14 in byte 15 | 16 bytes to 0x0CD48474 |
| 2 | the same sum of bytes 0..6 in byte 7 (CDJ-850: bytes 0..11 in byte 12) | 16 bytes to 0x0CD48484 |

No type byte is checked in either frame. `panel_unpack_buttons` (0x0C0C6804)
makes ten big-endian words at 0x0CD48494: w0..w6 from frame 1 bytes 1..14 and
w7..w9 from frame 2 bytes 1..6. Frame 1 is laid out as on the CDJ-850 (w1
rotary counter, w2/w3 tempo fader and centre, w4/w5 jog, w6 the word with
the ENTER/jog bits and the 0x20/0x40 power bits).

`panel_keys_to_internal_words` (0x0C0DA740) builds the key words K0..K2
(0x0CD48508..) from w7..w9. Matching each K bit with the CDJ-850's
0x0C0ECCB4 names the bits:

| Wire bit | K bit | CDJ-850 key with that K bit |
|---|---|---|
| w7 0x0100 | K2.3 | STOP (usb_stop) |
| w7 0x0200 | K0.13 | PLAY |
| w7 0x0400 | K0.14 | CUE |
| w7 0x0800 | K0.12 | LOOP IN |
| w7 0x1000 | K0.11 | LOOP OUT |
| w7 0x2000 | K0.10 | RELOOP/EXIT |
| w7 0x4000 | K0.9 | none |
| w7 0x8000 | K0.8 | none |
| w7 0x0001 | K2.2 | none |
| w7 0x0002 | K2.1 | none |
| w8 0x0100 | K2.12 | MENU |
| w8 0x0200 | K0.2 | TRACK SEARCH - |
| w8 0x0400 | K0.3 | TRACK SEARCH + |
| w8 0x0800 | K0.5 | SEARCH - |
| w8 0x1000 | K0.4 | SEARCH + |
| w8 0x0001 | K1.2 | EJECT |
| w8 0x0002 | K1.10 | VINYL |
| w8 0x0004 | K1.8 | MASTER TEMPO |
| w8 0x0008 | K1.9 | TEMPO |
| w9 0x0100 | K2.13 | TIME |
| w9 0x0200 | K1.3 | BACK |
| w9 0x0400 | K2.4 | none |
| w9 0x0001 | K0.0 | USB |
| w9 0x0002 | K0.1 | DISC |
| w9 0x0004 | K2.0 | LINK |

The K-bit names assume the two firmwares give each K bit the same meaning.
The emulator's `panel_buttons_350` table (`xc/panel_peer.c`) uses them; the
unnamed bits are `k0_9`, `k0_8`, `k2_2`, `k2_1` and `k2_4`. By the service
manual's key list (section 9.2 of the digest) the CDJ-350 keys without a
CDJ-850 counterpart are LOOP DIVIDE -/+, PLAYLIST and BPM LOCK; `k2_2` shows
`NO MASTERBPM`, so it is probably BPM LOCK (alias `bpm_lock`), and K2.0, the
CDJ-850's LINK, is probably PC. The previous-press copy of K0..K2 is K0 + 8
(0x0CD48510), not K0 + 0x1A as on the CDJ-850.

### How the keys act

`keys_handler_common` (0x0C0C826E) compares K0..K2 with the previous copy.

- **Source keys (USB, DISC, K2.0) act on a hold.** The press edge sets a
  timer in `key_hold_timers` (0x0CD48556) to 1000 and a bit in
  `key_hold_pending` (0x0CD48518); `keys_tick_1ms` (0x0C0C6EBC) subtracts
  100 every 100 ticks; when the timer reaches 0 with the key still down the
  source changes (`active_source_index` 0x0CD48D06: 0 disc, 2 USB). Release
  first cancels it. On the unit that is a 1 s hold.
- **The encoder push acts on release**, if released while its timer
  (`key_hold_timers` + 2) is still running.
- **Panel events.** The player loop (0x0C0DAC80) runs the unpacker itself
  and builds the key words when a panel event is pending and
  `keys_build_busy` (0x0CD48BED, set while the player waits on a request
  such as 0x0C0DC2F6) is 0. In `player_source_mode` (0x0CD48D0E) 1, on USB,
  the unpacker drops an event unless w1, w6 bit 0x20 or w7..w9 changed, except
  on every third event (counter 0x0CD484F0). The encoder push (w6 0x0100)
  therefore needs panel events to keep coming while it is held. The TXI1
  ISR's change test counts bits 0x0C of bytes 6 and 8, the tempo slider and
  centre ADC low bytes, so on the unit ADC noise supplies them. The
  emulator's panel adds that noise: every few transactions it raises both
  words by 4 together, which leaves the slider's offset from its centre
  unchanged (`CDJ350_PANEL_NOISE=0` turns it off, `=<n>` sets the period in
  transactions, default 3). Without it most pushes were lost; with it the
  load push worked every time.

### What the emulator does (`cdj350` machine)

| Input | Result |
|---|---|
| `eject` | `EJECT` |
| `bpm_lock` (`k2_2`) | `NO MASTERBPM` |
| `menu` / `utility` (w8 0x0100) | `DISC` over ` NO DISC` (message at 0x0C13E854, sent from 0x0C06124C) |
| `usb` held about 1 s | `USB` over `>ARTIST<`: the stick's rekordbox library (shorter holds do nothing) |
| rotary | steps ARTIST, ALBUM, TRACK, KEY ... |
| `push` on TRACK | the title list (long titles scroll) |
| `push` on a title | the track loads (title over artist); USB player state 0x0A browse, 2 loading, then 3 |
| playing (WAV test track) | the DSP receives the PCM and outputs it (peaks match the track's 0.2 tone); the time readout counts down |

Loading takes long here: about 13 s for a 46 s WAV and about 40 s for the
stock stick's MP3. While loading or playing an MP3 the CPU is busy in the
floating-point MP3 synthesis (0x0C12AE44), and QEMU emulates the SH-2A FPU in
software; while loading a WAV it is busy around 0x0C06E030 (per-sample work,
not identified).

The 1 ms RTOS tick (CMT0) used to run 500-800 times per emulated second on
both models: the tick handler's CMF acknowledge restarted the period, and a
compare match that came while the last tick was still pending merged into
it. `xc/cmt.c` now keeps the period's phase and replays such matches after
the acknowledge (`CDJ850_CMT_CATCHUP=0` turns the replay off), and both
models count exactly 1000 ticks per second. A USB hold now takes effect after
about 1 s, as on the unit.

In ordinary runs playback still runs slower than real time (0.35-0.6× by
the time readout) and loads are slow, because this host does not emulate a
200 MHz SH-2A fast enough, the more so under load from other work. With
QEMU's instruction-counted time at about the real chip's speed
(`-icount shift=2,align=off,sleep=off`: 4 ns per instruction) the CDJ-350
behaves as on the unit: the USB hold switches after 0.98 s, the WAV test
track loads 0.27 s after the push, and the time readout runs at 1.00× real
time. So the firmware and the emulated hardware keep up; only host speed
does not. While it plays there is almost no USB traffic: the CDJ-350 reads
the WAV into RAM when it loads it. `CDJ_USB_STATS=1` logs the stick's bytes
in and out per emulated second.

Instruction-counted runs are also the way to get repeatable timings on a
busy host (they take longer in wall-clock time). **Open:** the other
indicator pages (BPM, tempo, LEDs; Codex is decoding them on
`codex/cdj350-display`).

### MAIN to panel

Each transaction carries one of seven 32-byte slots at 0x0C9B850C, selected by
0x0CD70673. The six indicator slots have paired headers `n1` / `n2`, with
`n` from 1 to 6. The packing routine at 0x0C069058 writes the pages before
SCIF1 sends them. Its loop at 0x0C06904C stores the modulo-256 sum of slot
bytes 0..27 in slot byte 28 (frame 2 byte 12). The last three bytes are zero.
The emulator checks the header pair and the sum before updating the glass.

The seventh slot at 0x0C9B85CC contains two text rows of 16 wire bytes each,
one per frame. Code around 0x0C068866 writes them. Values `00` and `0A` pad
like spaces, and `81` / `82` mark the browse cursor. With no disc the rows are
`NO DISC` and a blank row. On USB they can show `USB` above `>ARTIST<`.

| Page | Frame 2 byte, zero-based | Display data |
|---|---|---|
| `11/12`, `21/22` | 11 on each page | Track tens and units. |
| `31/32` | 6–11 | Time digits MM SS FF, 75 frames per second. |
| `41/42` | 6 | Tempo sign (bit 1 enables the sign, bit 0 adds a vertical stroke), BROWSE (bit 2), LOCK (bit 3), TEMPO % (bit 4), leading tempo 1 (bit 7). |
| `41/42` | 7–8 | BPM hundreds and tempo units. |
| `41/42` | 9–10 | Panel LEDs, listed below. The deck app receives this second frame by UDP. |
| `51/52` | 6 | A.CUE (bit 0), BPM (bit 3) and the tempo decimal position (bits 4 and 5), and INFO (bit 7). |
| `51/52` | 7, 9, 11 | BPM tens, units and tenths. |
| `51/52` | 8, 10 | Tempo fractional digits. |
| `61/62` | 6–7 | REMAIN at byte 6 bit 0. Range at byte 7, with ±6, ±10 and ±16 on bits 7, 6 and 5 respectively when bit 4 is set. Bit 2 selects WIDE with bit 4 clear. |
| `61/62` | 8–11 | The low 30 bits are the playing-address bar, from left to right. MAIN sets the mask according to the time mode and applies blink timing. |

Page 4 frame 2 drives the button lamps. The renderer and deck app use the
current reported bits, so firmware-controlled blinking follows the frame
stream.

| Byte | Masks and lamps |
|---|---|
| 9 | `02` USB STOP, `04` COMPUTER, `08` CUE, `10` PLAY/PAUSE, `20` LOOP IN, `40` LOOP OUT, `80` USB source. |
| 10 | `01` RELOOP/EXIT, `02` DISC source, `08` the shared BEAT LOOP lamp between the two divide buttons, `10` MASTER TEMPO, `20` VINYL, `40` DISC EJECT. |

The panel CPU drives the bicolor POWER/STANDBY LED (D513, RRV4069 p.69).
The app shows green while valid page-4 reports arrive. Red hardware standby
remains outside the CDJ-350 panel emulator.

The wire masks for segments A through G are `01 02 10 40 20 04 08`. The
renderer displays the masks directly, including blank digits and flashing
readouts. On a 128 BPM WAV, setting a master BPM and pressing BPM LOCK
set page 4 byte 6 bit 3 through the reported lock flash, and unlocking
cleared it. Toggling DISPLAY between the track list and track information
swapped BROWSE and INFO. A separate capture at the positive fader limit
showed that range bytes `5B`, `3B`, `0F` and `9B` correspond to ±10, ±16,
WIDE and ±6. The LED mapping was checked with source selection, cueing,
loop adjustment, beat loop, eject, USB STOP and a run without USB media.

The glass layout follows the CDJ-350 service manual RRV4069 pp. 10–11 and the
display reference image. Its glyphs are drawn in software. The deck app uses
the same screen over loopback VNC. The chassis, switch placement and silver
jog rim follow the [CDJ-350 product photo](https://d1aeri3ty3izns.cloudfront.net/media/24/249125/1200/preview.jpg).

Indicator page 3 (`31` / `32`) carries the time readout in frame 2 bytes
6..11: six 7-segment digits MM SS FF (75 frames per second, REMAIN by
default). Segment codes: 0 `77`, 1 `12`, 2 `6B`, 3 `5B`, 4 `1E`, 5 `5D`,
6 `7D`, 7 `13`, 8 `7F`, 9 `5F`. The emulator decodes it into the display
window's time readout.

## USB FLAC playback

The [FLAC mod](../mods/flac/README.md) uses the stock WAV path. MAIN v1.14
classifies USB files at `0x0C03EB94` (type 11 for WAV). The USB file handle
is at `0x0C1ABC18`, with `0x0C1ABC1C` selecting the source (0 USB, 1 disc).
Both USB open size calls share the pool word at `0x0C055634`. The classifier,
six audio pool words, and startup loader are recorded in the CDJ-350 annotations.

MAIN's startup clears `0x0C1CC678–0x0DCC2D33`. The FLAC loader places
its source in that cleared tail at `0x0C1CC700`, copies the payload
through the uncached mirror to `0x0DE00000`, and chains to the stock clear
at `0x0C0AE3F4`. The decoder uses its own stack. The stock audio task's
stack is 6 KB. During playback the SH7263 model reported zero coherency
findings and no model warnings, with about 104 million payload instruction
fetches. The PCM ring is at `0x0C1D7710`.

The power-on keys pending byte at `0x0C1CAF4A` starts set. MAIN clears it
when it reads the power-on keys. The update-mode byte at `0x0C1CAF3D` then
holds 1 for USB or 2 for disc when the update keys were held. Each FLAC
hook falls back to its stock function while either byte is nonzero. Update
mode reads the version at file offset `0x60010`. The comparison at
`0x0C08575C` checks the first character and the two digits after the dot
when the first character is at least ASCII 1. A matching label skips the
write. The USB update writes 57 sectors starting at `0x60000`. The word-programming
loop at `0x0C084C28–0x0C084D1A` was observed while updating from stock
v1.14 to a FLAC build labelled v1.15 in QEMU. The updater displayed
`COMPLETE`, and the programmed firmware bytes matched the playback test image.

## Running it

Use `./start.sh --model cdj350` for the FL window or
`./start.sh --model cdj350 --app` for the full deck. Hold USB or DISC to switch
sources. Press Enter or click the rotary selector to choose an item and turn
the selector or use the up and down arrows to browse.

For a headless capture:

```sh
CDJ_MODEL=cdj350 MAIN_BOOT=flash FLASH=extract/cdj350/flash_cdj350.bin \
  scripts/run/boot_main.sh c350 30
```

The log shows each text change as `cdj350-panel: text [row 1] [row 2]`.
`CDJ850_PANEL_SCRIPT` takes the names in the table above; hold a source key
long enough, e.g. `CDJ850_PANEL_SCRIPT='9000:usb:1500,13000:rot+2,15000:push'`,
with a stick attached through `MAIN_ARGS` (see `launcher/deck.py`).
